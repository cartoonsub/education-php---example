## Слайд 2 — Зачем нужен POST

Начнём с главного правила, которое стоит запомнить сразу: **POST передаёт данные в теле запроса, а не в URL.**

Именно это одно отличие открывает нам три важные вещи.

Первое — мы можем передавать чувствительные данные: пароли, логины, токены. Они не попадают в логи сервера, в историю браузера, в кэши. Потому что их просто нет в адресной строке.

Второе — мы можем передавать большие объёмы данных. Например, JSON на несколько тысяч записей. У URL есть ограничение по длине, а у тела запроса — практически нет.

И третье — только через POST мы можем передавать файлы: PDF, картинки, CSV.

*[Небольшая пауза, чуть тише и серьёзнее]*

Но вот важная оговорка, которую я хочу проговорить отдельно. POST безопаснее GET именно в смысле «не светится в адресной строке». Но сам по себе POST **не шифрует** данные. Если вы отправляете пароль по обычному HTTP без HTTPS — его всё ещё можно перехватить. Реальную защиту даёт только HTTPS. Это не альтернатива POST, а его обязательный спутник.

## Слайд 3 — GET vs POST

Быстро освежим разницу между GET и POST, чтобы дальше было проще.

GET хранит данные в адресной строке — помните, что-то вроде `?name=Tom&age=36`. У него есть ограничение по размеру, он кэшируется браузером, его можно сохранить в закладки.

POST — противоположность по всем пунктам. Данные в теле запроса, ограничения по размеру практически нет, не кэшируется, в закладки его не сохранишь. И, конечно, только POST умеет передавать файлы.

Если коротко: GET — для *получения* данных, POST — для *отправки* и *изменения*.

## Слайд 4 — Анатомия POST-запроса

Теперь заглянем под капот и посмотрим, как POST-запрос выглядит на самом деле.

*[Указать на слайд с примером HTTP-запроса]*

Любой POST-запрос состоит из трёх частей.

Первое — URL, адрес, куда мы отправляем запрос.

Второе — заголовки, или headers. Это метаданные: например, `Content-Type` говорит серверу, в каком формате пришли данные.

И третье — тело запроса, body. Вот здесь как раз и лежат наши данные — `username=admin&password=12345`.

Обратите внимание на заголовок `Content-Length` — сервер должен заранее знать, сколько байт весит тело, чтобы понять, где данные заканчиваются. И на пустую строку между заголовками и телом — она строго их разделяет.

## Слайд 5 — Content-Type

А теперь ключевая идея всей темы: заголовок `Content-Type` определяет, **как именно** сервер разберёт то, что лежит в теле запроса.

Есть три основных варианта.

Первый — `application/x-www-form-urlencoded`. Это поведение по умолчанию для любой обычной HTML-формы без файлов. Данные кодируются так же, как в URL: пробелы становятся плюсом или `%20`. В PHP это автоматически превращается в `$_POST`.

Второй — `multipart/form-data`. Используется, когда нужно передать файлы. Данные здесь *не* кодируются — иначе файл раздулся бы в размере, — а разбиваются на блоки специальным разделителем, который называется boundary. Важно не забыть указать `enctype="multipart/form-data"` прямо в HTML-форме — без этого атрибута загрузка файлов просто не заработает.

*[Пауза, чуть выделить голосом]*

И третий вариант, про который дальше поговорим отдельно — `application/json`.

## Слайд 6 — Ловушка с JSON

Вот здесь я хочу остановиться подробнее, потому что это самая частая точка путаницы у новичков.

PHP **не умеет** автоматически парсить JSON в `$_POST`. Если ваш JavaScript отправляет данные через `fetch` с `Content-Type: application/json`, а вы на сервере попробуете достать их через `$_POST['username']` — вы получите пустоту. Массив просто останется пустым, даже если данные реально пришли.

Как читать JSON правильно? Вот так:

*[Указать на код]*

Сначала читаем сырое тело запроса через `file_get_contents('php://input')`. Затем декодируем его функцией `json_decode`, указывая вторым параметром `true`, чтобы получить обычный ассоциативный массив. И только после этого можем обращаться к `$data['username']`.

Запомните эту связку: `php://input` плюс `json_decode` — это единственный правильный способ поймать JSON на PHP.

## Слайд 7 — Практика: форма и файл

Переходим к практике. Разберём два самых частых сценария.

Сценарий первый — обычная форма. Мы достаём логин через `$_POST['username']`, проверяем метод запроса через `$_SERVER['REQUEST_METHOD']`, и выводим приветствие.

*[Пауза]*

Обратите внимание на функцию `htmlspecialchars` — это не украшение кода, а защита от XSS-атак. Если вывести пользовательский ввод на страницу без неё, злоумышленник сможет вставить в поле username свой скрипт, и он выполнится у других пользователей. Никогда не доверяйте вводу пользователя напрямую.

Сценарий второй — обработка файла. Проверяем, что файл вообще пришёл через `isset($_FILES['avatar'])`, забираем временный путь `tmp_name`, формируем путь назначения и перемещаем файл функцией `move_uploaded_file`.

Пока выглядит просто. Но дьявол в деталях — и мы до них ещё дойдём.

## Слайд 7.5 — Массивы в форме

Ещё один момент, который часто упускают. Что делать, если у нас несколько полей с одним смыслом — например, несколько чекбоксов «любимое блюдо»?

Решение простое: добавляем квадратные скобки в имя поля — `name="dish[]"`. PHP сам соберёт все отмеченные значения в обычный массив, и мы получим их через `$_POST['dish']`.

*[Пауза, предупреждающий тон]*

Но есть нюанс: если пользователь не отметил ни одного чекбокса, ключа `dish` в `$_POST` не будет вообще. Поэтому всегда пишем `$_POST['dish'] ?? []`, а не обращаемся к ключу напрямую.

И тот же трюк работает с файлами — `name="pictures[]"`. Но структура `$_FILES` в этом случае устроена не так, как ожидает интуиция. Это не массив файлов, а массив, где каждое поле — `name`, `tmp_name`, `error` — само становится массивом, индексированным по номеру файла. Значит, перебирать нужно через `foreach ($_FILES['pictures']['error'] as $key => $error)`, а не через `$_FILES['pictures'][0]['name']`, как многие пишут по привычке.

## Слайд 8 — Анатомия $_FILES

Разберём подробнее, что именно лежит внутри `$_FILES`.

*[Указать на структуру]*

`name` — оригинальное имя файла на компьютере пользователя. `type` — MIME-тип по мнению браузера. `tmp_name` — путь к временной копии файла на сервере. `error` — код ошибки. И `size` — размер в байтах.

Ключ `error` нужно проверять всегда, до того как что-либо делать с файлом. Вот основные коды: ноль — всё прошло успешно. Единица — файл превысил лимит из php.ini. Двойка — превышен лимит, заданный в самой форме. Тройка — файл загружен лишь частично. Четвёрка — пользователь вообще не выбрал файл. И шестёрка — на сервере не нашлось временной папки.

Запомнить все коды наизусть не обязательно — но привычку проверять `error` перед работой с файлом нужно выработать железно.

## Слайд 9 — Безопасность

А теперь самая важная часть видео — безопасность при загрузке файлов. Здесь ошибаются даже опытные разработчики.

Первое: поле `name` — **опасно**. Это оригинальное имя файла, которое пришло от пользователя. Злоумышленник может назвать файл, например, `../../../etc/passwd` или `script.php`. Если использовать это имя напрямую для сохранения на сервере — вы открываете дорогу для атаки. Правило простое: никогда не используем `name` напрямую, всегда генерируем собственное имя на бэкенде — например, через `uniqid()`.

Второе: поле `type` — тоже нельзя доверять. Его присылает браузер, и оно легко подделывается. Чтобы узнать реальный тип файла, используем расширение Fileinfo — функцию `finfo_file`, которая заглядывает в само содержимое файла, а не верит подписи снаружи.

*[Пауза, серьёзный тон]*

И третье — где хранить файлы. В идеале папка с загрузками должна лежать выше корневой директории сайта, чтобы к файлам нельзя было обратиться напрямую по URL. Если такой возможности нет — обязательно настройте сервер так, чтобы в папке `/uploads/` было запрещено исполнение любых скриптов. Иначе загруженный `script.php` можно будет просто открыть в браузере — и он выполнится.

## Слайд 10 — Итог

Подведём итог всего, что сегодня разобрали.

POST передаёт данные в теле запроса, а не в URL — это делает его подходящим для чувствительных и объёмных данных.

`Content-Type` определяет, как сервер разберёт тело запроса — это центральная идея всей темы.

`$_POST` прекрасно работает для обычных форм, но не работает для JSON — там нужен `php://input`.

И главное: любая загрузка файла от пользователя — это потенциальная уязвимость. Никогда не доверяйте `name` и `type` из `$_FILES` напрямую — проверяйте реальный тип файла и генерируйте безопасное имя сами.
